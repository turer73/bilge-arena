## Apply adımları

### 1. Pre-apply audit (read-only, prod'da güvenli)

Supabase Dashboard → SQL Editor:

```sql
-- Hangi tabloda authenticated SELECT var? (REVOKE öncesi snapshot)
SELECT table_name, string_agg(privilege_type, ',') AS privileges
FROM information_schema.role_table_grants
WHERE table_schema = 'public'
  AND grantee = 'authenticated'
  AND privilege_type = 'SELECT'
GROUP BY table_name
ORDER BY table_name;
```

**Beklenen çıktı:** Aşağıdaki 8 tablonun listede olması:
`profiles`, `session_answers`, `game_sessions`, `user_topic_progress`, `user_question_history`, `comments`, `comment_likes`, `challenges`

### 3. Apply

Supabase Dashboard → SQL Editor → New query → migration içeriğini yapıştır:

```sql
BEGIN;

REVOKE SELECT ON public.profiles               FROM authenticated;
REVOKE SELECT ON public.session_answers        FROM authenticated;
REVOKE SELECT ON public.game_sessions          FROM authenticated;
REVOKE SELECT ON public.user_topic_progress    FROM authenticated;
REVOKE SELECT ON public.user_question_history  FROM authenticated;
REVOKE SELECT ON public.comments               FROM authenticated;
REVOKE SELECT ON public.comment_likes          FROM authenticated;
REVOKE SELECT ON public.challenges             FROM authenticated;

COMMIT;
```

**Run.** "Success" mesajını gör.

## Kapsam dışı (bilinçli)

Bu migration **8 tabloyu** REVOKE eder. Şunlar **kapsamda değil**:

- **questions**: `page.tsx` landing ISR `getGameCounts()` cookie supabase üzerinden okuyor. Apply için önce page.tsx service-role'a geçmeli. Riski düşük (ISR; sadece counts; sayı 0 dönerse boş alan görünür) ama gelecek sprint işi.
- **user_roles, role_permissions**: `src/lib/supabase/admin.ts` `checkPermission()` cookie context kullanıyor; REVOKE = admin paneli + tüm admin API route'ları 403. `admin.ts` helper'ları service-role parametresi alacak şekilde refactor edilmeli. Gelecek sprint işi.
- **proxy.ts** middleware: zaten service-role REST API fallback'i var (`proxy.ts:69-89`). REVOKE'tan etkilenmez.
