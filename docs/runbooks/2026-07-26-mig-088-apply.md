# Migration 088 Apply Runbook

**Migration:** `database/migrations/088_repair_award_badges_concurrency.sql`

**Purpose:** Replaces the production `award_badges(UUID, TEXT[])` function with the race-safe implementation. Only badge rows actually returned by `INSERT ... ON CONFLICT DO NOTHING RETURNING` can receive XP. A concurrent loser therefore receives no badge and no XP ledger entry.

**Risk:** Medium. The migration changes a `SECURITY DEFINER` RPC used after solo sessions and by the badge endpoint. The database function must be updated before any consumer deployment that depends on its atomic award response.

## Required deployment order

1. Keep the consumer/API deployment that uses the new badge flow out of production.
2. Apply migration 088 and complete the post-apply checks below.
3. Run the synthetic concurrency smoke test.
4. Only then deploy the API/client consumer changes (`/api/sessions`, `/api/badges`, and the solo session saver).
5. Confirm a normal solo session returns HTTP 200 and can show a newly earned badge toast.

Do not reverse this order. Deploying a consumer first leaves a window where concurrent badge calls can still invoke the previously applied, unsafe function body.

## Preflight

- [ ] Schedule a low-traffic window and identify the on-call owner.
- [ ] Confirm the intended consumer build has passed CI, but has not yet been promoted ahead of migration 088.
- [ ] Confirm `SUPABASE_SERVICE_KEY` is available to the operator. `SUPABASE_SERVICE_ROLE_KEY` is accepted only as a legacy fallback by the smoke script.
- [ ] Confirm `node database/lint-migrations.mjs` is clean.
- [ ] Confirm no unrelated SQL is pasted into the SQL editor transaction.

Run this read-only audit in Supabase SQL Editor before applying:

```sql
SELECT
  p.oid::regprocedure AS signature,
  pg_get_functiondef(p.oid) AS definition,
  array_to_string(p.proacl, E'\n') AS acl,
  p.proconfig
FROM pg_proc p
JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'public'
  AND p.proname = 'award_badges';
```

Record the result. The function must have the `public.award_badges(uuid,text[])` signature. If the function is absent or its signature differs, stop and investigate rather than applying a modified migration.

1. Open Supabase Dashboard -> SQL Editor -> New query.

## Post-apply database checks

Run this read-only audit:

```sql
SELECT
  p.oid::regprocedure AS signature,
  pg_get_functiondef(p.oid) LIKE '%ON CONFLICT (user_id, achievement_id) DO NOTHING%' AS conflict_safe,
  pg_get_functiondef(p.oid) LIKE '%RETURNING achievement_id%' AS returns_inserted_rows,
  pg_get_functiondef(p.oid) LIKE '%public.increment_xp(p_user_id, v_total_xp, ''badge_earned'')%' AS atomic_xp_path,
  array_to_string(p.proacl, E'\n') AS acl,
  p.proconfig
FROM pg_proc p
JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'public'
  AND p.proname = 'award_badges';
```

Expected:

- Exactly one `public.award_badges(uuid,text[])` row.
- `conflict_safe`, `returns_inserted_rows`, and `atomic_xp_path` are all `true`.
- `proconfig` contains `search_path=public`.
- Execute permission is granted to `service_role`; `anon` and `authenticated` do not have execute access.

## Synthetic concurrency smoke test

This command writes to production only after the explicit confirmation value is set. It never selects an existing user. It creates a unique synthetic auth user, waits for its profile trigger, performs two simultaneous `award_badges(first_game)` calls, and hard-deletes the synthetic auth user in `finally`.

From the repository root, with the production URL and service key already available in `.env.local` or the environment:

```powershell
$env:ALLOW_PROD_BADGE_SMOKE = 'I_UNDERSTAND_PROD_WRITE'
node database/smoke-award-badges-concurrency.mjs
Remove-Item Env:ALLOW_PROD_BADGE_SMOKE
```

Success criteria:

- The command prints `PASS` and exits 0.
- Exactly one RPC response is the winner: `['first_game']`, `50` XP.
- Exactly one RPC response is the loser: `[]`, `0` XP.
- The synthetic user has exactly one `first_game` achievement.
- The synthetic user has exactly one `xp_log` row with `reason='badge_earned'` and `amount=50`.
- The profile's total XP changes by exactly `+50`.
- No cleanup error is printed; the synthetic auth user is hard-deleted and dependent rows cascade.

If the command fails, do not deploy the consumer. Preserve its output, confirm cleanup status, and investigate with a forward fix.

## Consumer deployment and application post-check

After the smoke test passes, deploy the intended consumer build. With a non-production test account:

1. Complete a solo quiz that crosses a badge threshold.
2. Confirm `POST /api/sessions` returns HTTP 200 and contains `newBadges`.
3. Confirm the badge toast is displayed from that response, without a second solo `POST /api/badges` request.
4. Confirm total XP increases once for the badge and the profile lists the achievement.
5. Confirm multiplayer completion still uses its existing `/api/badges` flow.

## Safe rollback

Do **not** restore the earlier `award_badges` function body or any implementation that catches `unique_violation` and still awards XP. That would reintroduce the double-XP race.

If the consumer rollout has a regression after migration 088:

1. Revert the API/client consumer deployment to the last compatible application release.
2. Leave migration 088 in place; it is the safe database state.
3. Diagnose and ship a forward fix in a new migration and application deployment.

There is intentionally no SQL rollback to the unsafe function. Do not delete migration history or manually replace the function with a pre-088 definition.
