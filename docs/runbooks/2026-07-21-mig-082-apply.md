# Migration 082 Apply Runbook

**Migration:** `database/migrations/082_single_question_stats_writer.sql`
**Amaç:** `questions.times_answered`/`times_correct` sayaçlarının çift-sayımını (disc#1370, konu#7 S3) durdurmak — `update_question_stats()` trigger-fonksiyonundan `questions` UPDATE bloğu kaldırılır, tek yazar `batch_increment_question_stats` (migration 022, `complete_game_session` RPC'sinden nested çağrılır) olarak kalır. `user_question_history` upsert'i aynen korunur.
**Risk:** DÜŞÜK — bu migration **kod değişikliği GEREKTİRMEZ, koddan bağımsız uygulanabilir**. `complete_game_session` RPC'si (migration 081) ve route.ts'e dokunulmuyor; yalnız bir trigger-fonksiyonunun gövdesi değişiyor, trigger'ın kendisi (`trg_answer_stats`) ve imzası aynı kalıyor. `/api/sessions` akışı kesintiye uğramaz, oturum kaydı hiçbir aşamada bloklanmaz.
**Deploy-sıralama (ÖNEMLİ):** Bu migration, **repair script'inden (`database/repair-question-stats-2.sql`) ÖNCE** uygulanmalı. Sıra ters olursa: repair tam-recompute yapıp sayaçları doğru değere çeker, ama migration henüz uygulanmadığı için repair'den SONRA gelen her cevap yine trigger + RPC'den çift sayılmaya devam eder — onarım anlık olarak doğru görünür, sonraki ilk cevapla tekrar bozulur. Doğru sıra: **082 apply → post-apply audit (aşağıda) → repair-question-stats-2.sql çalıştır**.
**Geri alma:** Migration dosyasının sonunda hazır (eski trigger-fonksiyon gövdesini geri koyan `CREATE OR REPLACE FUNCTION`) — rollback çift-sayım bug'ini GERİ GETİRİR (bkz. rollback bloğu uyarısı).

## Apply adımları

### 1. Pre-apply audit (read-only, prod'da güvenli)

Supabase Dashboard → SQL Editor:

```sql
-- Cift-sayimi gosteren ornek sorgu: tek-cevapli bir soruda sayac beklenenden
-- BUYUK olmali (trigger + RPC ikisi de saydigi icin). En az bir satir donmesi
-- beklenir (disc#1370'in kanitladigi durum).
SELECT q.id, q.times_answered, q.times_correct, real_counts.gercek_answered
FROM questions q
JOIN (
  SELECT question_id, COUNT(*) AS gercek_answered
  FROM session_answers
  GROUP BY question_id
  HAVING COUNT(*) = 1
) real_counts ON real_counts.question_id = q.id
WHERE q.times_answered <> real_counts.gercek_answered
ORDER BY q.times_answered DESC
LIMIT 20;

-- update_question_stats fonksiyonunun mevcut govdesinde "UPDATE questions" gecip
-- gecmedigini dogrula (beklenen: apply-oncesi 1 satir, govde icinde "questions" gecer)
SELECT prosrc FROM pg_proc WHERE proname = 'update_question_stats';
```

**Beklenen:** İlk sorgu, tek cevaplı sorularda `times_answered > 1` gösteren en az bir satır döner (çift-sayım kanıtı). İkinci sorgu, mevcut fonksiyon gövdesinde `UPDATE questions` bloğunun hâlâ var olduğunu gösterir.

## Geri alma (rollback)

```sql
BEGIN;
CREATE OR REPLACE FUNCTION public.update_question_stats()
RETURNS TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path TO 'public'
AS $$
BEGIN
  UPDATE questions SET
    times_answered = times_answered + 1,
    times_correct  = times_correct + (CASE WHEN NEW.is_correct THEN 1 ELSE 0 END)
  WHERE id = NEW.question_id;

  INSERT INTO user_question_history (user_id, question_id, times_seen, times_correct, last_seen_at)
  VALUES (NEW.user_id, NEW.question_id, 1, CASE WHEN NEW.is_correct THEN 1 ELSE 0 END, NOW())
  ON CONFLICT (user_id, question_id) DO UPDATE SET
    times_seen    = user_question_history.times_seen + 1,
    times_correct = user_question_history.times_correct + CASE WHEN NEW.is_correct THEN 1 ELSE 0 END,
    last_seen_at  = NOW();

  RETURN NEW;
END;
$$;
COMMIT;
```

(Eski gövde `database/full-schema.sql:553-570`'ten alınmıştır.)

**UYARI:** Bu rollback, disc#1370'in çift-sayım bug'ini GERİ GETİRİR — `trg_answer_stats` yeniden `batch_increment_question_stats` ile birlikte aynı cevabı iki kez sayar. Ayrıca repair (`repair-question-stats-2.sql`) zaten çalıştırılmışsa, rollback sonrası gelen her yeni cevap sayaçları tekrar kirletmeye başlar (sayaç geçmişi yeniden bozulur). Yalnız bu migration'ın beklenmedik bir yan-etkisi tespit edilirse ve hızlı bir forward-fix mümkün değilse kullan.
